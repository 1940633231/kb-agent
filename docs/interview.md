# 面试问答与设计取舍

配套材料在 `README.md`（架构、流程、逐轮实测数据）。这里只写**要讲清楚的话**与**要认的账**。

## 一句话定位

在已有检索底座之上，用 LangGraph 构建一层具备自我纠错与人工介入能力的知识问答编排层，
用自建 A 股年报语料把检索从"够用"做到"可靠"，并给出可测量的提升。

三个仓库的分工：`production-rag` 证明"会把检索做扎实"（向量/BM25/RRF/Rerank/评估），
`sql-mcp-agent` 证明"懂工具、权限与可观测"，本项目证明"会让 Agent 变可靠"。

## 常用数字（都要记得住，别背错）

- 语料：3 家公司 × 3 年 = 9 份年报，正文 2,279,449 字符 → **3,576 个 chunk**（recursive，chunk 800/overlap 120）
- 检索配置：`bge-small-zh-v1.5`（512 维）+ FAISS flat（精确检索）+ jieba BM25 + RRF + `bge-reranker-base`
- 评测集：**50 题**（事实 12 / 表格 10 / 跨章节 9 / 跨文档 9 / 计算 5 / 应拒答 5），每题回原文核对、带出处页码
- 测试：**67 个用例**（含跨进程重启恢复、interrupt 恢复与幂等、SSE 事件流、评分与裁剪的纯逻辑）

## 1. 为什么用 LangGraph，而不是 if/else 或单 Agent 循环

if/else 编排在"要不要重试、重试几次、中断怎么恢复"上会迅速退化成散落各处的状态判断；
而单 Agent 循环（ReAct）把判定权全交给模型，成本与可解释性都不可控。

LangGraph 给的是：**显式 State**（哪些字段累积、哪些覆盖，靠 reducer 定死）、
**条件边**（判定逻辑是代码，不是提示词）、**checkpointer**（线程执行进度可持久化、可恢复），
以及 `interrupt`（把人工介入做成流程的一等公民）。这个项目的核心差异点正是"判定与恢复"，
所以选它。

## 2. Checkpointer 和 Store 的区别（高频追问）

| | Checkpointer | Store |
|---|---|---|
| 存什么 | 某个线程执行到哪了（State、下一步、待审中断） | 跨线程仍然成立的记忆（偏好、业务约定） |
| 生命周期 | 随线程，服务于恢复与继续执行 | 跨会话长期有效 |
| 隔离维度 | `thread_id` | `("kb-agent","users",{user_id},"memories")` |
| 不是 | 聊天记录表，也不是知识库 | 知识库文档的收纳处 |

本项目两者都实测过：**另一个进程**用同一 `thread_id` 读回并累加状态（重启恢复），
以及 alice 写一条偏好、新进程读到、bob 读到 0 条（namespace 隔离）。

## 3. 条件重试到底有没有用（**最重要，也最容易被问穿**）

先分清两层，不要混：

- **相对单路向量基线，提升很大**：文档级 Recall@5 从 0.842（L0）到 0.974（L2）。
  但这主要是 **L1 混合检索 + L2 重排**的功劳，属于"检索层"，不是 Agent 层的。
- **L3（自纠错）相对 L2 的增量**：文档级 **≈ 0**（L2 已经 1.000/0.941 量级饱和），
  证据级（答案需要的数值是否都进了证据）**+0.105**。

诚实结论：**在这份语料规模上，编排层的净收益体现在"多轮把证据补全"，而且只在跨文档多值题
（"宁德时代2023与2025年营业收入分别是多少"）这类问题上体现**。要讲的那个数字就是它，
不要包装成"Agent 大幅提升检索"。

为什么只有这么点：L2 之后文档级已经饱和，剩余错误**主要在生成侧**——
拿了母公司报表的口径、把亿元/万元换错 10 倍、多值题只答一半。
证据是：LLM 语义复核判定"证据够"的那两道题（茅台 2023 营业收入、2025 归母净利润），
复核给出的理由是可以逐条核对的（片段里确实有 14,769,360.50 万元；四个季度归母净利润
加总正好是 82,320,067,101.68 元）。

## 4. 生成侧修复为什么最后没开

我实现了"生成后复核 + 一次 LLM 校订"（`agent/repair.py` + `verify_answer` 节点），
然后用 LLM 裁判的裁决离线交叉验证触发条件：

| 交叉结果 | 题数 |
|---|---|
| 判错且会被修复命中 | 5 |
| 判错但漏网 | 1 |
| **判对却会被改动（误伤）** | **11** |
| 判对且正确放过 | 2 |

修 5 道真错要动 11 道本来对的答案 → **默认关闭**（`enable_answer_repair=False`），
代码与 7 个单测保留，触发条件收紧方向也写清楚了（只对"整个证据里都找不到的数字"触发）。
这题的价值在于回答方式：**用数字否掉自己刚写完的功能**。

## 5. 人工介入怎么做的、边界在哪

`interrupt()` 挂起（payload 带 `review_id`、问题、失败原因、证据摘要、草稿答案）→
另一个进程用 `Command(resume=...)` 恢复；实现里补了三件容易被忽略的事：
**幂等**（同一 `review_id` 重复提交返回同一结果，不会被后一次 decision 覆盖）、
**校验**（review_id 与当前挂起项不一致直接拒绝）、**超时**（提交时判定过期）。

边界：并发只做了**进程内**串行化，多副本需要数据库层互斥（如 `SELECT ... FOR UPDATE`），
属"明确不达标"。

## 6. 引用可信怎么量

两个不同的量，别混：

- `citation_coverage`：答案里的数字有没有出现在**被引用**的片段里 → 引用可信度。
- `grounding`：被引片段是否与问题指标相关（用最长指标词作锚）→ 抓"选错指标/选错表"。

并且明确它**不是错误率**：实测标出的题里，一部分是答案错（引了现金流量表的净利润），
一部分是答案对但引用没覆盖到那个数字（引用问题）。所以只做标记、不参与路由。

## 7. 度量上踩过的三个坑（主动讲，显得可靠）

1. **L2 根本没走重排**：评估脚本只调了 `retriever.search()`，拿到的是"更宽候选池 + RRF 排序"，
   于是 L2 的数字虚高。改成复刻 pipeline 的检索段（候选池→活跃版本过滤→重排→截断）后才可信。
2. **`covered` 变量复用**：引用覆盖的列表覆盖了"文档交集"，`doc_recall` 算出 3.72 这种不可能的值。
3. **证据/答案的字面量口径**：计算题的期望值是算出来的（"616.89 亿元"），
   拿它做字面匹配会误判；改成用 `evidence_literals` 声明原文真实出现的数字，
   答案判定再做单位归一化（元/千元/万元/百万元/亿元互转）。

这三条合起来说明一件事：**度量不可信时，后面所有"提升"都不成立**。

## 8. 明确没做到的生产能力（被问就直说）

容量与 SLA（QPS、可用性）、多副本高可用、任务队列、Prometheus/Grafana 生产观测、
审核工作台前端、复杂记忆提取/遗忘/冲突处理、多 Agent 协作——都在方案里列为"不做"，
不是遗漏而是范围决策。另外已知短板：单题 35~75s（瓶颈是 CPU 上的 Cross-Encoder 重排）、
50 题规模下单次运行有约 ±0.1 的波动、生成层数字与模型版本强绑定（换模型要重测）。

## 9. 如果继续做，下一步是什么

1. 收紧生成侧修复的触发条件（只对"整个证据里都找不到的数字"触发），再用裁判口径复测。
2. 生成侧约束升级：不要求模型自行换算单位，改为"逐字引用 + 标注所在表格"。
3. 压重排延迟（候选池裁剪 / 批量重排 / 换 API rerank），这是 SSE 体验的瓶颈。
4. 把技术问答（LangGraph 官方文档辅库）与多轮/记忆题纳入评测——目前 50 题全部是可判定的
   单轮题，因为要保证分母可信；技术问答题需要裁判口径，单独一套 harness 更合适。

## 10. 可能被追问的细节

- **为什么 chunk 800/overlap 120**：年报表格行被 PDFium 拍平成行文本，800 字符约覆盖
  一张小表的若干行；overlap 120 防止关键行被切断。语料总量只有 3,576 chunk，
  所以 FAISS 用 flat 精确检索，不需要调 IVF/HNSW 参数。
- **为什么 top_k=5**：与 L0~L2 对齐保证可比；L3 重试轮会放宽到 15 并按 chunk_id 追加合并。
- **为什么重试上限是 2**：方案定的；实测超过 2 轮后追加证据的边际收益接近 0，
  而每题多一轮重排要多花约 25~30s。
- **为什么有 5 道拒答题**：用来量"该不该答"，而不是只量"答得对不对"；
  实测 3/3（现 5 道待测）都正确拒答，且分数阈值永远拦不住它们——
  这是"评分必须看要素覆盖，不能只看相似度"的实测依据。
- **为什么改 PDF 解析**：招商银行年报用字体子集且缺 ToUnicode，`pypdf` 抽出来是乱码
  （206,412 字符、"营业收入"命中 0 次），PDFium 抽出 392,667 字符、命中正常；
  只换"PDF→文本"这一步，切片/向量化仍复用 production-rag，保持单条管线。
